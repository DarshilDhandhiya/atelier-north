# Design note

## Direction
Atelier North is a small studio. The site should feel like a good architectural monograph: calm, spacious, confident about its photography. Choices were made from the architecture world rather than from generic website templates.

**Signature element:** the *title block*, borrowed from the corner panel of an architectural drawing sheet, presents project facts (location, year, area, category) in a ruled box. The hero also carries a vertical *dimension line* beside the image. Everything else stays quiet.

## Design system (source: `frontend/src/styles/tokens.css`, live page: `/design-system`)

**Colour** – Basalt `#1b2224` (text), Limewash `#eef1ec` (page), Limewash 2 `#e3e8e1` (alternate sections), Stone `#cbd1ca` (image placeholders), Fjord `#25565c` (primary action), Fjord 700 `#1a4247` (hover), Fjord 100 `#d9e7e5` (info), Birch `#d9cbb0` (quiet accent), Danger `#9b2626`, Success `#25603d`, Focus `#1f6feb`. Contrast: body text on page 14.6:1, Fjord on page 7.1:1, white on Fjord 7.8:1, muted text 6.9:1. All meet WCAG AA, most AAA.

**Type** – Instrument Serif (display) with Hanken Grotesk (text), self-hosted via Fontsource (no third-party font requests). Fluid scale with `clamp()`: display 2.75–6.75rem, h1 2.5–5.25rem, h2 2.1–3.5rem, h3 1.5–2.1rem, body 17px/1.6, measure 66ch.

**Spacing and grid** – 4px base (4, 8, 12, 16, 24, 32, 48, 64, 96), max content width 1360px, fluid gutters 20–48px, section rhythm `clamp(4rem, 3rem + 6vw, 8rem)`. Tested at 360, 768, 1024 and 1440 px.

**Components** – buttons (primary, outline, danger, small, on-dark), links, filter chips (toggle buttons with `aria-pressed`), form fields with label/hint/error, selects, checkbox, file input, cards (image + text, no box), title block, accordion (native `details`), pagination (real links), alerts (success/error/warn/info), badges, skeletons, empty and error states, lightbox, toasts and confirm dialog (admin).

**States** – every data view has loading (skeleton), empty (what is missing + next action), error (what happened + retry) and success (confirmation with reference) states.

**Motion** – almost none by design: a skeleton shimmer and the mobile sticky CTA sliding in. Both are disabled under `prefers-reduced-motion`. **Persistent CTA:** the header carries a *Book a consultation* button at every width; below 1024px a sticky bottom bar also appears after the hero.

## Accessibility decisions
Skip link; semantic landmarks; route-change focus announcer; visible 3px focus ring on every control; labels (never placeholder-only); error summary that receives focus plus per-field `aria-invalid`/`aria-describedby`; form errors explain how to fix; lightbox is a modal dialog with focus trap, Esc, arrow keys, swipe, and returns focus to the opener; alt text required in the CMS (schema rejects images without it); 44px minimum touch targets; honeypot hidden from AT; links that open new tabs say so. Automated scan (axe-core, WCAG 2.0/2.1/2.2 A+AA tags): 0 violations on all 11 public routes. Automated tools find roughly a third of issues, so a manual screen-reader pass (NVDA/VoiceOver) before launch is recommended.

## Hi-fi designs
`design/mockups/` contains desktop (1440) and mobile (390) mockups for **Home, Project detail and Enquiry** (SVG + PNG), generated by `design/build-mockups.mjs` from the same tokens. They are code-generated, not Figma files; the Enquiry mockups deliberately show the validation-error state. Placeholder rectangles stand in for photography.

## Key engineering decisions
- **Enquiry is saved before anything else.** Email is a side effect: failure never loses a lead. The error is stored and retried with exponential back-off; staff can retry from the enquiry page.
- **Attachments in MongoDB, not on disk**, so they survive ephemeral hosting and are served only to admins with `nosniff` and a sandbox CSP. File types are verified by magic bytes, not by extension or declared MIME type.
- **One generic CRUD router** powers five content resources, so validation, publishing and ordering behave identically.
- **Shared option lists** for project type, budget and timeline come from the server (`/api/meta/enquiry-options`) so form and validation cannot drift.
- **Images** use CDN size parameters to build `srcset`, store dimensions to prevent layout shift, load lazily, and fall back to an inline SVG if a photo fails.
- **URL-driven filters** (`?category=&location=&q=&sort=&page=`) make every view shareable and back-button friendly.
- **CSRF**: cookie auth + required custom header + strict CORS allow-list. **Secrets** only from environment; app refuses to boot in production with a weak `JWT_SECRET`.

## Limitations
1. Client-side SEO tags (SPA). Search engines that run JavaScript handle it; link-preview bots often do not.
2. Rich-text editor uses `contentEditable` + `document.execCommand` (deprecated but universally supported). Output is sanitised server-side; swap for TipTap/Lexical for heavy editorial use.
3. Single studio language (English) and no CMS versioning/drafts-history.
4. Rate limiting is in-memory per API instance. Use a shared store (Redis) if you run several instances.
5. Demo photography is stock; maps are a link, not an embedded map (avoids third-party cookies).
6. Email delivery retries run in-process; for high volume use a queue.
7. Not tested against live Cloudinary or live SMTP in development.

## Recommended next steps
- Pre-render or server-render public routes (Vite SSG, or Next.js) for social cards and faster first paint.
- Image pipeline that generates AVIF/WebP variants on upload.
- Draft preview links, scheduled publishing UI, revision history.
- Multilingual content (English/Norwegian).
- Redis-backed rate limiting and a job queue; Sentry for error monitoring.
- CAPTCHA (e.g. Turnstile) if spam appears despite the current controls.
- A manual WCAG audit with assistive technology users.
